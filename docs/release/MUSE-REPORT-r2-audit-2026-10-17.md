## 1. B5 — interrupted-hand fairness record: **PASS**

Verified by Muse's own execution: the Phase 1 battery passes 12/12 including `fair_after_interrupt`, and the test passes 3/3 standalone runs — each kills the server after the flop of hand 3, restarts on the same store, replays hand 3 under the same number with a new deck, and the interrupted deal remains on record as `void: 'interrupted'` and verifies (verifier sealOk, bad=0, void=1; non-void hand numbers contiguous). Code read confirms the mechanism: the deal record is written at deal time and on each street under the same key the finished record later overwrites (`server/fair.js` `saveDeal`/`saveHand`/`fkey`); `resume()` converts leftover live records via `voidLive`; `report()` surfaces any other leftover as `void: 'unfinished'`; chips, replay, and poker rules are unchanged, and old reports verify as before. Persistence rides the same store abstraction as all game state (PostgreSQL in staging/production), and the flush is awaited (bounded 1 s) before cards are published (`server/club.js`).
Residuals (accepted, not blockers): a crash inside the ≤1 s flush window can still lose the in-flight street's record — the owner-approved latency trade-off; the flush adds a database round trip per street, so hand pace on Render Postgres must be observed on staging after the deploy (Claude's own flag, and §9 includes it in the smoke checks).

## 2. B6 — owner PIN reset, session invalidation, lockout protection: **PASS**

Code read (`server/index.js`) confirms: `resetOwner` sets the new PIN, then `revokeSessions(id)` deletes every stored session for the owner and closes open sockets with code 4003; every subsequent socket message re-checks the socket's own session (`ws.sess`), so a revoked token cannot act on an already-open connection; the setup code is compared in constant time (`crypto.timingSafeEqual`); recovery failures are limited per source address (5 per 10 min) with a club-wide cap (60 per 10 min), and only wrong-code errors count. Muse's own run of `t_sessions_owner_reset` passes with the exact intended shape: one address 400×5 then 429; twelve wrong codes from twelve addresses do not lock the owner out (owner then succeeds, 200); the club-wide cap trips at 61. Member removal now uses the same revocation helper (B7 behaviour preserved, covered by the same test).
Residual MINOR (documented by Claude, accepted for R2): the per-name login limit (10 wrong PINs) can still be tripped by a stranger against a member's name for 10 minutes; the owner always retains the setup-code recovery path. Follow-up for the backlog: any future "owner resets a member's PIN" feature must call `revokeSessions`.

## 3. Chat isolation and cross-user data leakage: **PASS**

Muse executed `test/t_chat.js` himself: **passed, 1,849 checks**, with itemized no-delivery proofs (828 deliveries correctly withheld from players at other tables, 162 from signed-out sockets, 139 from railbirds of other tables, 110 from lobby members, 78 from removed members, 41 from the owner when not watching). Code read of the delivery paths agrees with the test's model: chat and throws route only to sockets seated at or watching the sender's table; chat logs are per-table and deleted on table close; hole cards go only to their seated owner. One genuine minor leak was found by Claude and is fixed in this code: the table-`closed` notice previously went to every socket including unauthenticated ones; it now goes to signed-in sockets only (verified in the diff). Cross-user leakage on the club surfaces is covered by the content suite's visibility checks (unauthenticated calls return 401 with no data; contact fields reach other members only when the member switched them on), all green in Muse's full-suite run.

## 4. F1 — contact-content filter (owner decisions applied): **PASS with MINOR findings**

The owner's three decisions are implemented as specified: direct phone numbers and emails are blocked in opportunity contact-request messages; business names are checked while legitimate names are preserved; social handles, profile links, and messaging IDs are blocked (owner revision of 2026-10-17), with the sanctioned sharing path (the reply/share step) still allowing a member to deliberately share their own email/phone. Muse ran an independent 39-probe corpus against `server/content.js` (beyond Claude's 201-probe suite, which also passes in Muse's full run): every direct-contact form was blocked — six phone formats including fully spelled-out digits, three disguised email forms, handles, profile links, `wa.me`, DM invitations, bare domains — and all 17 legitimate business texts were allowed, including "Studio 416 Interiors", "Highway 7 Auto Sales", "$1,500,000 / 2 500 000 sq ft", postal codes, and platform-name prose ("Facebook ads management", "Instagram: 10k followers").
MINOR findings (all usability/robustness, none a staging blocker): misses match Claude's disclosed known-limits list (non-Latin decimal digits, letter-for-digit swaps) plus one Muse addition — comma-separated phone numbers (`416,829,5953`) are not caught; false positives are the disclosed ones (comma-less number lists such as "Sizes 10 12 14 16", bare 8-digit order numbers), mitigated by the error message's rephrasing hint and by director moderation. Gate condition (not a staging blocker): run `scripts/content-audit.js` against production data before either club is opened — records saved before the rule are unfiltered until edited.
