## Conditions
1. **MEDIUM — latent data loss inside the isolation layer.** A scoped `set('user:…')` for a non-main club rebuilds the membership record from only the membership fields present in the value passed, instead of merging: Muse's unit probe turned `clubs[B] = {role:'owner', joinedAt, invitedBy}` into `{muted:true}` with one partial write — role, joinedAt and invitedBy silently destroyed. **No current caller triggers it** (club modules never write `user:` records; every index.js scoped write spreads a scoped `get` first), but this is a one-line-away footgun in the security layer itself — worst case, a club owner's role is wiped and they are locked out of their own Director. **Fix before production activation** (merge picked fields over the existing membership record); recommended before staging use grows beyond testing.
2. **Composition:** the branch's server baseline matches production (5c7ee11 + privacy hunk), but its client predates the table redesign — any production path requires a rebase onto `4423a07` (or successor) + new SHA + Muse delta re-audit. Standard for all outstanding branches.
3. **Rollback semantics (disclosed by Claude, confirmed):** if a second club is ever used and the flag is later removed or old code restored, `noMain` accounts become plain main-club members under the old code. Needs an owner decision + cleanup procedure before any production use. No impact while flag-gated.
4. **STAGING=1 enables the feature** (`server/clubs.js:11`), consistent with the dev+staging authorization — but "staging" is not flag-neutral for this branch; deploying it to staging/preview activates switching there. Recorded so nobody is surprised.
5. **Test-evidence note:** the handoff's "CLUB_SWITCHING=1 npm test exit 0" is timing-dependent — the flag-ON chain died once in `t_extra`'s fixed 700 ms boot sleep, and `t_opportunity` has a pre-existing 150 ms flush race (byte-unchanged by this branch; passes with a settle wait). The per-suite results above are the reliable evidence form. Same harness-fragility class as the standing finding.

Shared-by-design (not leaks): identity layer (name/PIN, sessions, avatars by id as in baseline, push subscriptions, the club-definition list, and each user's own club list) is shared across clubs — that is the approved "one identity" model. Fairness lookups search only the asker's club.
