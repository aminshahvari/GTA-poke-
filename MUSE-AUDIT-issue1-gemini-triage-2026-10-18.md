## Headline answers
- **P0 race condition: NOT ACTIVE in production.** The fenced-husk remediation is IN the production baseline (it reached `main` after the `p0-deploy-race` branch work; the phase1 tests exist identically in `integ4` and on `origin/main`), and Muse's fresh phase1 run on the production-baseline tree passes **12/12**, including `lease_lost_stays_alive`, `restart_pingpong` (epoch 1→2, exactly one handover, zero restarts) and `sigterm_after_loss` (exit 0 in 13 ms). Production `server/index.js:451-480`: on lease loss the process freezes the store, closes sockets 4001, answers 503, never re-claims, exits only on SIGTERM. Live `/healthz` all day: postgres mode, epoch 1, leaseLost false. What remains open from the P0 package (README §3) is verification, not the defect: two staging deploys with clean handovers were never run, Risk 7.3 (Render SIGTERM behaviour toward a live-but-503 process) is unchecked, and neither Render service has the `/healthz` health-check path configured. Those need owner authorization for staging merges/config — they do not block production as it stands.
- **Production persistence: NOT at risk from the ignored-directory concern.** Production persists to Postgres under a single-writer lease (`server/store.js`: lease claimed in one transaction at boot with epoch bump and claim-before-load fencing; every flush re-locks the lease row and aborts permanently on epoch mismatch; heartbeat 3 s). The `.gitignore` `data/` entry governs only file mode (`data/club.json`), which is the local-dev/test path — `DATABASE_URL` set ⇒ Postgres mode; production env (verified read-only Oct 17) sets it. The preview service runs file mode, which is correct for a preview. Genuine residual risks, stated plainly: (i) the production Postgres **expires 2026-11-14** (BR-QLT-03 — the real persistence deadline); (ii) a fenced instance answers 503 until SIGTERM (by design; pairs with the unverified Risk 7.3 above); (iii) the fresh-backup artifact discipline is still owner-side (G4).
- **Reconnection integrity: NO reproducible integrity issue.** Phase1 `reconnect` PASSES on the production baseline: on `hello` the server re-sends the pending turn (same seq, legal actions, original deadline — not reset) plus the player's own cards, and an act on the new socket applies. Hidden-card privacy is structural: the shared snapshot carries cards only for shown showdown hands (`club.js` `snapshot()`), and hole cards reach a client only via `cardsFor(tid, uid)` keyed to the requester's own uid (`server/index.js` `pushTable`). One disclosed limitation, NOT an integrity defect: the server sends no ack/nack for acts, so an act sent into a dead socket is lost silently (the client cannot distinguish lost from slow). Recorded in `t_reconnect.js` itself; recommend as a backlog UX/robustness item.
- **Per-table concurrency (in-process): SOUND by construction + test.** One Node process, one club instance, one waiter per player uid; `club.act()` resolves only on exact tid/hand/seq match — duplicates, stale and out-of-turn acts return false and change nothing (`club.js:260-267`). Phase1 `duplicate_actions` PASSES (18 duplicate sends + stale acts ignored; points match history for all 5 members), `two_instances` PASSES (only one instance dealt; state not clobbered). Chip conservation was separately verified in the final poker audit (3-handed drive 3,289 snapshots clean; heads-up forensic 4,886 checks clean).
- **Mobile viewport (concern 4): REAL historically, fixed in the audited release line, not yet in production.** The jumping defect (height-coupled layout, no dvh/visualViewport) was fixed in `8eee0a5`; the redesign's hero-overlap P1 failed `443a27f` and is closed in `330863f` (CONDITIONAL PASS) and its descendants `958e7c0` / `4423a07` (PASS). Production `5c7ee11` still contains both the jumping behaviour and the old layout — concern 4 closes for members only when tonight's gated release (or a later one) ships. Evidence: verdict files in `~/workspace/blindrise-audit/`.
